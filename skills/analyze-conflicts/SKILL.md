# Step 3 — analyze conflicts and decide with the BA

You are a senior business analyst acting as the BA's analysis partner. Load `ba-rules` first and follow it — especially golden rules 3 (never invent) and 4 (the BA decides trade-offs), the decision rules (§3) and the architect rule (§7). Read `ba-project.yaml`.

## Gate
- `steps.requirements.status` is `reviewed` or `approved`. Otherwise stop and tell the BA.
- If `analysis-log.md` exists:
  - `Status: Reviewed`/`Approved` → do not regenerate; changes now go through `/ba-sync`.
  - `Draft` with conflicts `Open` or gaps without a BA answer → **resume Part B** from the first undecided item; do not redo Part A.

## Inputs
`docs/01-requirements/requirements.md` (incl. §8 observations), every `docs/00-source/NN-*.md`, `docs/00-source/README.md`, `ba-project.yaml` (`people`, `decisions.proxy_for_sponsor`, `decisions.max_ab`, `stack.deploy.profile`, `project.deadline`).

## Output
`docs/02-analysis/analysis-log.md` from `templates/analysis-log.md` in this skill's directory. Header per golden rule 8 (`Generated by: analyze-conflicts (BA kit)`, date, inputs with `Confluence <pageId> v<N>`, `Status: Draft`).

## Part A — analysis (write, do not decide)

| § | Section | Rules |
|---|---|---|
| 1 | **Conflicts (`CON`)** | Two positions that cannot both be fully satisfied. Each: position A and B (who, quote, `[KEY · Section]`) · why they conflict · what is at stake for the PoC · linked IDs · **2–3 options** (description · pros · cons · effect on scope) · `Claude's recommendation` with the proposed outcome (a/b/c) · `Status: Open`. Include conflicts the sources already resolved: record the resolution as a prior `DEC` with its source and check whether it created new questions (new scope always needs details and acceptance criteria). |
| 1 | **Architect rule candidate** | Run `ba-rules` §7 now. If `stack.deploy.profile` is `static` or `local` and any REQ/NFR/DEC needs state shared between devices or users (use requirements §8 item 7 as the starting list, then check every row against the signs in §7), write one `CON` tagged **`Architect rule`**: position A = the shared-data requirements (IDs, quotes); position B = the deploy profile from `ba-project.yaml` and any stakeholder constraint against servers, cloud or maintenance (quotes). Options always compare `static` (with the requirement explicitly narrowed for the PoC, e.g. single-device demo + seed data + UI banner + `ASM`), `local`, `cloudflare`; outcome (c) is also possible. If the profile is `cloudflare` or `none`, or no requirement needs shared data, write one line in §2 saying the rule was checked and why it does not fire. |
| 2 | **Goal-vs-constraint check** | Table: every element of the definition of done and of the business problem · source · constraints in play · achievable? · item. Any mismatch is a `CON` or `RSK`. |
| 3 | **Gaps (`GAP`)** | Missing information as a concrete question to a **named** stakeholder (as written in the sources) · why it matters · linked IDs · `Status: Open`. Unconfirmed `Derived` requirement rows are listed here as questions for the BA. |
| 4 | **Source inconsistencies (`SI-n`)** | Dangling references, numbers without basis, contradicting statements, ambiguous statuses — with both sources. |
| 5 | **Risks (`RSK`)** | Risk · owner · impact · mitigation. Include the risk to `project.deadline` if scope grows. |
| 6 | **Assumptions (`ASM`)** | Only those needed to proceed; each `ASSUMPTION — not validated`, with owner and "what changes if wrong". |
| 7 | **Decision log (`DEC`)** | Prior decisions from `requirements.md` §6 referenced, not copied. New DECs only in Part B. |
| 8 | **Open questions for the sponsor** | Filled in Part B from outcome (c) and open gaps. |

**Every observation in requirements §8 must land somewhere** — as a CON, GAP, SI, RSK or ASM, or in a short list "Observations not carried forward" with the reason. Report the mapping count.

Quote rules are those of the `requirements` step: verbatim fragments, `[KEY · Section]` references that exist in `docs/00-source/README.md`.

Write the file with Part A complete before starting Part B, so the BA can read it while deciding.

## Part B — decisions with the BA (decision point H2)

Go through **each `Open` conflict, one at a time** — the architect-rule CON included:
1. Summarise it in the chat language in 3–5 lines: positions, options, `Claude's recommendation`.
2. Ask the BA for the option **and** the outcome — (a) Decided, (b) Prototype both (A/B), (c) Deferred — sponsor decision (use the question tool if available). Suggest (b) only for conflicts that are key to the demo; warn if more than `decisions.max_ab` conflicts would end up as A/B.
3. Record the answer as `DEC-xxx`: conflict · `Outcome` · decision · rationale · affects (REQ/NFR/CON/OOS) · `Decided by: <people.ba> (BA[, proxy for <people.sponsor>])` · date. Set the conflict to `Resolved` (a), `Resolved — A/B` (b) or `Deferred` (c). Note in the run log whether the BA chose differently from the recommendation.
4. For (b): describe variant A and variant B precisely enough to write stories for each, and name the switch the sponsor toggles at the demo.
5. For (c): add the item to §8 "Open questions for the sponsor".
6. If a decision creates or changes requirements, add rows to `requirements.md` as `Proposed` with source `[DEC-xxx]`; mark affected rows `Superseded by …` / `Refined by …` — never overwrite. Add a `Revised` line to its header.
7. **Architect-rule DEC:** if the BA's decision changes the deploy profile, ask for an explicit OK to change `stack.deploy.profile` in `ba-project.yaml`, then change it and append to `approvals` (`{step: conflicts, status: profile-change, by, date, note: DEC-xxx}`). If the outcome narrows the requirement, add the narrowing as `ASM` (`ASSUMPTION — not validated`) and a `Proposed` REQ/NFR (e.g. the UI banner).

Then the gaps: for each `Open` GAP the BA either answers (as proxy — record a `DEC`), converts it to an `ASM`, or leaves it open for the client (→ §8). Unconfirmed `Derived` rows: the BA confirms or rejects them; update their status in `requirements.md`.

Never decide for the BA; never record a DEC the BA did not confirm in this conversation. If the BA stops midway, keep the file as `Draft` with the remaining items `Open`; `/ba-continue` resumes here.

## Quality bar (check before finishing; report failures)
- Every CON has 2–3 options, a labelled recommendation and a status; no CON is `Open` at the end of Part B.
- Every DEC has outcome, `Decided by`, date and links; A/B count ≤ `decisions.max_ab` or the BA accepted the excess explicitly.
- Every quote is found verbatim in its source (Grep); every ID referenced exists.
- The architect rule was checked (CON or the one-line "does not fire" note).
- Every requirements §8 observation is mapped.

## Finish
1. `ba-project.yaml`: `steps.conflicts = {status: draft, source_version: <source.version>, updated: <today>}`.
2. Append to `docs/run-log.md`: counts (CON / GAP / SI / RSK / ASM / DEC), A/B used, decisions that differ from the recommendation.
3. Reply in the chat language: counts, the decisions table (CON → outcome), open sponsor questions, what the BA should check first, the decision point "BA review → reviewed", proposed commit `step 3: conflicts analysed and decided`. `write-stories` starts only when no conflict is `Open` and this step is `reviewed`.
