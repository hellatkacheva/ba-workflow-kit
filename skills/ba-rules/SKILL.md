# BA workflow kit — shared rules

Every kit command and step skill follows these rules. The project's `ba-project.yaml` holds the project-specific values (site, page, Jira key, people, language, deploy profile). Never hard-code them in artifacts or instructions.

Project templates used by `/ba-new` live in this skill's directory: `templates/project/`.

## 1. Golden rules

| # | Rule |
|---|---|
| 1 | **Sources are read-only.** Never edit anything in `docs/00-source/` except through the `ingest-confluence` skill, which only adds new snapshots and regenerates the working source files. Never write to the source Confluence page. |
| 2 | **Trace everything.** Every requirement, conflict, decision and story cites its source as `[KEY · Section]` (source key · section heading) plus a short verbatim quote. Source keys are listed in `docs/00-source/README.md` → "Source keys". No source → it is not a requirement. |
| 3 | **Never invent facts.** Missing information is a **Gap** (concrete question to a named stakeholder) or an **Assumption** — labelled `ASSUMPTION — not validated`, with an owner. |
| 4 | **BA decides trade-offs.** Claude never resolves a trade-off between stakeholders (or between a requirement and the deploy profile). Present 2–3 options with pros/cons and a labelled `Claude's recommendation`, then ask the BA. Record the decision only after the BA confirms, with `Decided by` and date. |
| 5 | **PoC, not production.** Smallest scope that meets "done". Flag gold-plating. Respect explicit out-of-scope items. |
| 6 | **Track change over time.** Later sources or source versions can reverse earlier items. Mark the earlier item `Superseded by …` — never silently overwrite. |
| 7 | **Stable IDs, never reused** (table below). |
| 8 | **Status on every artifact:** header with `Generated by`, date, inputs, source version (`Confluence <pageId> v<N>`) and `Status: Draft | Reviewed | Approved`. Only the BA moves a file to `Approved`. |

## 2. IDs

| Prefix | Meaning | Prefix | Meaning |
|---|---|---|---|
| `REQ-001` | functional requirement | `GAP-001` | gap / question |
| `NFR-001` | non-functional requirement | `ASM-001` | assumption |
| `CST-001` | constraint | `RSK-001` | risk |
| `OOS-001` | out of scope | `EP-1` | epic |
| `DEC-001` | decision | `US-001` | user story |
| `CON-001` | conflict | `CHG-001` | source change report |

## 3. Decision rules

Every conflict (`CON`) ends in exactly one outcome, chosen by the BA:

| Outcome | Meaning | Record |
|---|---|---|
| **(a) Decided** | BA decides (as proxy for the sponsor if `decisions.proxy_for_sponsor: true`). | `DEC-xxx`, `Decided by: <people.ba> (BA[, proxy for <people.sponsor>])`, date, rationale. CON → `Resolved`. |
| **(b) Prototype both (A/B)** | Both options built behind a switch; sponsor chooses at the demo. At most `decisions.max_ab` conflicts. | `DEC-xxx`, outcome `Prototype both (A/B)`. CON → `Resolved — A/B`. |
| **(c) Deferred — sponsor decision** | Not built; carried to the sponsor as an open question. | `DEC-xxx`, outcome `Deferred — sponsor decision`. CON → `Deferred`. |

## 4. Steps, statuses and gates

| Step key (`steps.<key>`) | Skill | Output | BA decision point |
|---|---|---|---|
| `ingest` | `ingest-confluence` | `docs/00-source/` | — (BA reads the report) |
| `requirements` | `requirements` | `docs/01-requirements/requirements.md` | BA review → `reviewed` |
| `conflicts` | `analyze-conflicts` | `docs/02-analysis/analysis-log.md` | BA decides each CON and GAP |
| `stories` | `write-stories` | `docs/03-backlog/` | BA answers open questions (OQ); backlog stays `draft` until the review step |
| `review` | `review-backlog` | `docs/03-backlog/review.md` | BA accepts / rejects findings, then backlog → `reviewed` |
| `spec` | `spec` | `docs/04-spec/` | spec questions (OQ-S); architect-rule re-check (§7); BA + tech review → `reviewed` |
| `build` | `build` | `app/`, `docs/04-spec/build-status.md` | BA accepts each story; all wanted stories accepted → `reviewed` |
| `deploy` | `deploy` | URL (or local run instructions), smoke test | explicit OK for every public deploy in the current conversation |
| `jira` | `jira-sync` | Jira + `docs/05-jira/jira-map.md` | OK on the plan before any write; sprint created by the BA |

Step status values: `not_started` · `draft` · `reviewed` · `approved` · `stale` · `skipped`.

- A step may start only if the previous step is `reviewed` or `approved`. Exceptions: `ingest` has no gate; `requirements` needs `ingest` ≥ `draft`; `review` needs `stories` ≥ `draft` (the critic reviews the draft backlog, as in the reference project); `deploy` needs `spec` ≥ `reviewed` and every Core demo story accepted by the BA (later stories are redeployed one by one); `jira` needs `review` ≥ `reviewed` only. Profile `none`: `spec`, `build`, `deploy` → `skipped` on the BA's OK. Otherwise stop and tell the BA.
- A skill sets its own step to `draft` when it writes output. Only the BA's explicit words ("OK", "reviewed", "approve") move a step to `reviewed` / `approved`; then append to `approvals` (`{step, status, by, date, note}`).
- **Waived gate.** When the BA waives a decision point in the conversation ("собери все истории сразу", "don't stop", "commit each", "без моего OK на каждую"), the step skill **at once**, before going on, appends to `approvals` `{step, status: gate-waived, by: <people.ba>, date, note: "<gate, e.g. H6> waived — '<BA's words>'; scope: <items, e.g. US-005…US-013>"}`, marks every item done under the waiver in its artifact as "done without BA check — pending" (e.g. `build-status.md` column BA), and at the end of the run lists those items and asks the BA for the deferred check. A waiver covers only the scope the BA named, only in this conversation, and never the actions in §6 (public deploy, secrets, Jira deletes, writes to Confluence).
- Requirement row statuses: `Confirmed` · `Proposed` · `Derived — needs BA confirmation` · `Superseded by …`. An unconfirmed `Derived` row is not agreed: later steps do not build stories on it and list it as a question for the BA.

## 5. ba-project.yaml protocol

- Read it at the start of every command and skill. If it is missing, say so in the chat language and suggest `/ba-new <confluence-url>`.
- MCP tools are called as `mcp__<atlassian.mcp_server>__<tool>` with `cloudId: <atlassian.cloud_id>`.
- Update only the fields your step owns (`steps.<key>.*`; `source.*` for ingest; `stack.constraints` for spec; `stack.deploy.url` for deploy; `jira.statuses` and `jira.sprint` for jira-sync). Never change `approvals`, `people`, `decisions`, `stack.deploy.profile` without the BA's explicit OK in the current conversation.
- Keep comments and field order when editing; edit in place, do not regenerate the file.

## 6. Actions Claude never takes on its own

| Never | Instead |
|---|---|
| Public deploy (GitHub Pages, Cloudflare prod) without an explicit OK in the current conversation | Show the command, wait for OK. Earlier approvals do not carry over. |
| Ask for, read, print, write or commit secrets (API tokens, `wrangler secret`, `.dev.vars`, GitHub Secrets) | The BA types them: `! gh secret set …`, `! npx wrangler secret put …` |
| Delete Jira issues, or touch anything outside `jira.project_key` | Label `superseded` + comment |
| Write to the source Confluence page (or any Confluence page) | Questions go to the analysis log / CHG report |
| Resolve a stakeholder conflict, or pick/change the deploy profile when requirements contradict it | `CON-xxx` → options → BA decides |
| Set any artifact or step to `approved` | Propose `reviewed`; BA approves |
| Rewrite artifacts in `/ba-sync` before the BA's OK on the CHG plan | Only snapshot + CHG report |
| `git push --force`, rewrite history, push without the BA asking | Commit after each step; push on request |

## 7. Architect rule (used by `analyze-conflicts`, `spec` and `change-impact`)

If `stack.deploy.profile` is `static` (no shared data — browser `localStorage`) or `local` (Node + SQLite on one laptop, shared only within that laptop / Wi-Fi) **and** any REQ/NFR/DEC needs state shared between devices or users (a shared limit or capacity, one resource lent/booked to one person, a shared stock or log, one role confirming another user's action, history/audit over time, seeing other users' actions), then:

1. Create `CON-xxx`: position A = the requirement (quote, source); position B = the deploy profile (`ba-project.yaml`, its DEC, stakeholder constraints such as "no servers").
2. Compare `static` / `local` / `cloudflare` with pros/cons and `Claude's recommendation`; outcome (c) Deferred is also possible.
3. **Stop.** Do not write the spec until the BA picks an outcome; record it as `DEC-xxx`.

Never silently narrow the requirement, silently switch profile, or add a third-party shared store without a DEC.

Where it runs: `analyze-conflicts` raises it first (Part A, candidate `CON` tagged `Architect rule`) and the BA decides it in Part B with the other conflicts. `spec` re-checks before writing and raises a new `CON` only for shared-data needs not covered by an existing architect-rule `DEC` (for example, requirements added after step 3). `change-impact` re-checks on C2/C3/C4 changes.

## 8. Language, git, run log

- Artifacts in `language.artifacts` (default `en`); conversation and step summaries in `language.chat` (default `ru`). End every step with a short summary in the chat language: what was produced, counts, what the BA must check first, proposed commit message.
- After each step propose a commit `step N: <what>`. Commit only when the BA agrees; never push unless asked.
- Append one row per run to `docs/run-log.md`: date · step · who ran it · duration · output · BA changes / notes.
